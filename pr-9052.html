PR #9052 Live Verification

PR: openshift/hypershift#9052  |  Bug: OCPBUGS-93739  |  Date: 2026-09-24  |  Status: deletion tested — result inconclusive on this cluster (see §5)

What the PR does: On AWS, when a HostedCluster is deleted, the hosted-cluster-config-operator (HCCO) now reads the guest LoadBalancer Service status and directly deletes the associated classic ELB / ELBv2 load balancers and target groups (scoped to the cluster's VPC and Services, not every LB in a shared VPC), then removes the non-ingress LoadBalancer Services. This prevents the teardown timeout reported in OCPBUGS-93739. HCCO also uses a short-lived web-identity token (kube-controller-manager service account + the existing cloud-controller role); the CPO IAM role is not expanded.

3a. Version-pairing notes (two issues found and fixed)

The PR's CPO is built from main and targets LatestSupportedVersion = 5.1.0. Two setup issues surfaced — both about pairing versions correctly, not defects in PR #9052:

  • Release payload skew: a first attempt used an old 4.21.9 release. The 5.1 CPO renders --tls-min-version/--tls-cipher-suites on payload sidecars (konnectivity proxy-server, aws-pod-identity-webhook) whose 4.21.9 binaries reject those flags → unknown flag: --tls-min-version CrashLoopBackOff. Fixed by using a matching 5.1.0-ec.0 release.
  • Management-operator gate: the released management operator supports max OCP 4.22.0, so it rejected 5.1.0-ec.0 (ValidReleaseImage=False). Fixed with the intended pre-release annotation:
oc annotate hostedcluster -n clusters pr9052-lb2 \
  hypershift.openshift.io/skip-release-image-validation=true --overwrite
ValidReleaseImage=True | Release image is valid

5c. Why it leaked — HCCO never ran the cleanup

PR #9052's cleanup lives in the HCCO resources controller (destroyCloudResources → ensureAWSLoadBalancersRemoved), which only runs once the HCCO controller-manager starts and its caches sync. On this cluster HCCO was crash-looping the entire time:

"if kind is a CRD, it should be installed before calling Start",
"kind":"MachineSet.cluster.x-k8s.io",
"error":"failed to get restmapping: no matches for kind \"MachineSet\"
         in version \"cluster.x-k8s.io/v1beta2\""
failed to wait for inplaceupgrader caches to sync
         kind source: *v1beta2.MachineSet: timed out

controller-runtime aborts the entire manager when any watched cache fails to sync, so the manager never started and destroyCloudResources never executed once. The LB leaked because the cleanup code never ran — not because it ran and did the wrong thing.

5d. Root cause of the crash-loop (a version-skew artifact, not a PR defect)

Only the test HC's CPO/HCCO were pinned to the 5.1 PR image, on a management cluster whose operator is 4.22-era (MCE-managed, registry.redhat.io/multicluster-engine/hypershift-rhel9-operator, max supported OCP 4.22.0). The 4.22 CAPI CRDs serve cluster.x-k8s.io/v1beta1; the 5.1 HCCO watches v1beta2 MachineSet. That mismatch is unrelated to the load-balancer feature — it just prevents HCCO from booting.

Verdict: inconclusive on this cluster. We proved the image build, the surgical CPO/HCCO pinning, and the customer-path teardown mechanics — but the actual LB-cleanup code path was never exercised, because HCCO could not start under the management-operator version skew. This is not evidence that PR #9052 is broken, and it is not a validation of it either. A conclusive test needs a management cluster whose CAPI CRDs match the PR (a 5.1-matched management operator) so MachineSet v1beta2 resolves and the HCCO resources controller boots.

Next step: reinstall this cluster's (MCE-managed) HyperShift operator with the PR image so the CAPI CRDs advance to v1beta2 and HCCO runs, then repeat the oc delete test and confirm the guest ingress ELB is removed automatically.

6. Retest on a version-matched management cluster

To exercise the actual cleanup code path, the management operator itself was switched to the PR (5.1) image so its CAPI CRDs match what HCCO expects. On this MCE-managed cluster that is done with the supported image-override ConfigMap (the addon re-applies it on a ~2 min loop):

  name: hypershift-override-images
